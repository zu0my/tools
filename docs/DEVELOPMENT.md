# 开发约定

## 环境

当前开发目标为 Windows，命令通过 PowerShell 7（pwsh.exe）执行。项目已有 Cargo.toml，使用 Rust 2024 edition。

开始实现前检查 rustc 和 cargo 是否可用，以及工具链是否支持当前 edition。确切工具链版本、Windows 链接工具和最低系统版本，在首次构建验证后记录；当前尚未验证。

如果缺少 Rust、链接工具或其他必要环境，说明缺失项，由用户决定是否安装，不自行下载。只有实际依赖 Node.js 工具时才涉及 pnpm；版本不符可以先尝试 corepack enable。

## 一个功能的开发流程

1. 从 [工具设计模板](tools/TEMPLATE.md) 创建工具文档，先写清问题、输入输出和不做的事情。
2. 明确最小可用范围，补充核心流程伪代码与验收场景。
3. 用户实现一个可运行的小步骤；助手按 [学习与协作](LEARNING.md) 提供解释、提示和审查。
4. 根据本次改动验证编译、行为和必要的错误路径。
5. 更新工具文档中的实现状态、用法和限制，并登记到工具目录。

不要求先完成所有架构层，也不一次实现全部计划功能。

## 验证范围

绝不在每次改动后执行全量测试脚本。默认根据影响范围选择验证，只有局部检查无法覆盖真实影响时才考虑全量测试，并说明必要性。

| 改动 | 合适的验证 |
| --- | --- |
| 仅修改文档 | 检查相对链接、事实、占位符与状态描述 |
| 修改纯计算逻辑 | 运行相关模块或精确指定的测试 |
| 修改参数解析或输出 | 验证对应命令的正常、帮助与错误场景 |
| 修改 Windows 交互 | 在 Windows 上验证相关成功与失败场景，避免影响真实重要数据 |
| 修改共享逻辑 | 覆盖实际受影响的工具，必要时扩大范围 |

测试关注可观察行为和有意义的边界，不为复述实现而编写测试。对文件等资源的测试优先使用临时数据。只读文档改动无需运行 Rust 构建或测试。

编译检查、格式检查和静态检查按改动需要执行；报告实际运行的检查及其结果，未执行的检查不声称通过。

## Git 协作

- 同步与整合代码使用 rebase，不使用 merge。
- 修改前了解已有工作，保留与本次任务无关的用户改动。
- 提交围绕一个明确目的组织，描述变化与原因。
- 未收到指令时，不自行提交或推送。

## 文档维护位置

项目定位写入根 README；共同接口写入 CLI；职责和取舍写入架构；工具特有行为写入对应工具文档。学习文档记录推进方式与理解目标，不逐条保存聊天记录或重复 Rust 教材。
