# 学习与协作

## 起点与目标

用户已经了解 Rust 基础语法和部分生命周期知识，尚未完成过完整项目。本项目通过实用 CLI 工具，练习需求拆解、模块组织、所有权与借用的实际运用、错误处理、系统交互、测试和交付。

不按语法目录重新学习一遍。每次遇到具体问题，再解释相关概念与取舍。

## 协作边界

- Rust 生产实现由用户完成。
- 用户于 2026-11-05 明确授权助手直接编写本轮删除预览测试；这项授权不包含预览生产实现。已有预览测试由助手添加，续接时无需再让用户重写，后续代写范围遵循用户最新指令。
- 助手提供需求澄清、设计建议、伪代码、解释、调试提示和代码审查。
- 未经用户明确调整要求，助手不生成、补齐或修改可直接使用的 Rust 实现，也不运行会生成源码的项目脚手架。
- 伪代码描述数据、步骤、分支和责任边界，避免用完整 Rust 语法变相交付实现。
- 用户明确要求的项目文档可以直接创建和维护；文档授权不等于源码生成授权。

## 推进节奏

| 阶段 | 产出 | 理解目标 |
| --- | --- | --- |
| 定义一个工具 | 简短设计文档与验收场景 | 把实际问题转成明确契约 |
| 跑通最小流程 | 一个可执行的成功路径 | 理解入口、数据流与调用关系 |
| 处理失败 | 可理解的错误和稳定的退出行为 | 理解 Result、错误传播与上下文 |
| 调整结构 | 按实际职责拆分模块 | 理解可见性、所有权边界与依赖 |
| 验证与交付 | 局部测试、真实调用和用法说明 | 理解测试范围与用户可见行为 |

这些是推进顺序，不代表每一步都要新增文件或引入 crate。

## TDD 与指导粒度

- 采用红、绿、重构的方式推进；一轮围绕完整行为规则组织，覆盖正常和边界场景，不机械地把每个选项或每个断言拆成单独回合。
- 每轮说明修改哪些文件、各模块的职责、涉及的标准库和第三方 crate、API 的用途、测试名称、输入、预期结果、实现伪代码及局部测试命令。不要假设用户熟悉 Rust 标准库或项目组织。
- 用户请求审查时先查看最新代码；审查通过且无待处理问题时，直接开始下一轮指导，不等待单独的“继续”。用户临时要求只解释语法或记录进度时，以该要求为准。
- 运行测试时确认实际执行的数量，不把空测试体通过或筛选到 0 个测试当成功能验证。回归测试可以直接通过，不人为制造红灯；新增行为应确认测试因正确原因失败。
- 保持前期结构精简，按真实职责拆函数或文件，不提前设计通用框架。
- 用户有意保留 ..RemoveOptions::default()，以便新增字段时自动补齐默认值，不把这一选择当成需要消除的问题。当前场景验证的字段尽量明确写出，其他字段可用默认值补齐。

## 提示和审查方式

遇到问题时，先说明观察到的行为与原因，再给出下一步提示和伪代码。涉及借用、移动或生命周期时，结合当前数据为何存在、由谁拥有、何时释放来解释。

审查优先关注正确性、错误处理、职责划分和惯用表达。区分必须修复的问题与可选改进；不为了练习复杂特性而引入不必要的泛型、trait、异步或 unsafe。

每个小阶段结束时，确认能否解释输入从哪里来、数据由谁持有、失败如何传递、结果如何输出，以及如何验证行为。
