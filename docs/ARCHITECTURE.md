# 架构与决策

## 当前实现

当前保持单一 Cargo 二进制包，使用以下模块：

- src/main.rs：声明 cli、remove 模块；main 仍只输出 Hello, world!，尚未连接真实参数、输出与退出码。
- src/cli.rs：parse_args 接收 &[OsString]，通过 split_first 分派；parse_remove_args 解析删除参数。返回 Command、RemoveOptions 或 ParseError，不访问文件系统。
- src/remove.rs：删除逻辑模块，目前 remove_path 仍固定返回成功，两个测试函数尚为空体。
- Cargo.toml：普通依赖为空；开发依赖 tempfile = "3.27.0"，只在测试模块中使用。

当前结构足够，不提前增加 workspace、trait 框架或多层目录。以下完整执行职责与数据流仍是后续实现方向。

## 职责边界

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| 程序入口 | 接收参数、分派命令、呈现结果、设置退出码 | 不堆积具体工具的业务逻辑 |
| 工具逻辑 | 校验业务输入，组织操作，返回结果与错误 | 尽量不直接打印，不依赖参数解析方式 |
| Windows 交互 | 访问文件系统、进程或其他操作系统能力 | 隔离平台细节，保留底层错误信息 |

按功能逐步拆分模块。单个工具很小时，可以在同一模块内区分职责；出现真实复用或测试需要时再拆分。暂不建立 Cargo workspace，也不预先抽象公共框架。

## 数据流

以下为设计伪代码，尚未实现：

~~~text
读取命令行参数
如果请求帮助或版本：输出对应信息并成功退出
解析并校验参数
选择对应工具
调用工具逻辑，必要时访问 Windows 能力
如果成功：把结果写入标准输出
如果失败：把带上下文的错误写入标准错误
根据结果设置退出码
~~~

具体命令的输入、结果模型、操作副作用和失败恢复方式，由对应工具文档定义。

## 错误与平台边界

- 可预期的用户输入错误和系统调用失败，通过错误返回交给入口处理。
- 保留操作对象、失败阶段和底层原因，避免只返回“操作失败”。
- 不用 panic 处理预期失败；是否增加错误类型或第三方库，由实际需求决定。
- Windows 路径在代码中优先使用 Path / PathBuf，避免假设路径总能转成 UTF-8 字符串。
- 如果确实需要 unsafe 或调用 Windows API，限制使用范围，并解释必须维持的安全条件。

## 依赖选择

先判断标准库是否足够，再评估第三方 crate。引入依赖时说明它解决的问题、选择理由和维护成本；在实际选型时核对其官方文档与 Windows 支持情况。当前不预定参数解析、错误处理或终端输出库。

## 已确定的决定

| 决定 | 原因 | 重新评估的条件 |
| --- | --- | --- |
| 使用 Rust，提供 CLI | 实用工具开发与完整项目学习是共同目标 | 项目目标变化 |
| 当前只支持 Windows | 控制首个完整项目的范围 | 出现实际跨平台需求 |
| 保持单一 Cargo 包 | 现阶段功能尚少，优先保持结构简单 | 多个独立产物或包边界带来明确收益 |
| 按需拆分模块和引入依赖 | 避免在实现前建立过多抽象 | 出现真实重复或职责混杂 |
